The disk is an ordinary bootable AmigaDOS volume — 50 catalogued files, the standard OFS filesystem, a two-line startup-sequence that boots to Workbench, and a marble-shaped icon the player double-clicks. There is no monolithic binary: a small launcher pulls in the 175 KB main program, and the running game streams each course's overlays — tile map (.mlb), sprite banks (.ilb/.vlb), gameplay layout (*Track) and sound bank (*Snd) — through the operating system's own LoadSeg as the course starts.

A file read without its name

The main program, c/MarbleMadness!.dat, is a genuine file in the disk's directory — yet the string MarbleMadness!.dat appears nowhere in the launcher. It is never opened by name. Instead a second-stage loader, c/xxx, drives the floppy hardware directly — CIA step and select lines, Paula disk DMA pulling a full 14,066-byte raw MFM track in one burst — and reads the program's bytes off the platter by physical position, reimplementing the operating system's disk driver from scratch. The file exists so the volume stays a valid, bootable AmigaDOS disk and its 360 data blocks are reserved contiguously (tracks ~93–126); it is read by location for speed, and because a from-scratch reader is also a copy-protection hook.

Dead code that pulled its weight

The launcher contains a complete, byte-identical copy of the decryptor's engine that is never called — not one control-flow reference reaches it. It was dragged in by the linker because one routine in the same object module is used: a checksum that EOR-folds the decrypted loader's hunks into a 16-bit constant and feeds it into the decryption key for the next stage. Tampering with the loader corrupts the key — a small integrity chain, with 6 KB of accidental cargo.
