What these emulators support

These are educational, experimental emulators. You can select an unfamiliar image, but that does not guarantee it will boot or render correctly. Game files stay on your computer. The site downloads emulator code, artwork and C64/Amiga firmware.

PSP uses Allegrex / VFPU, kernel HLE and software GE rendering. No PSP firmware file is needed. MPEG videos and audio are not decoded; compatibility remains limited by the existing Go core. The current PSP inspector records GE commands, framebuffer writes and rejection tests. It does not yet record per-texel ancestry. Its replay shows the final display buffer being built; offscreen targets are recorded but do not have a separate viewer.

Game Boy and Game Gear need no firmware files. They provide scanline tile/sprite rendering and historical tile/palette writes. The DMG core supports ROM-only and MBC1; Color-only and other mappers are not implemented. Game Gear uses the inherited instruction-budget scheduler, with approximate timing; line interrupts, alternate mappers, SRAM and link cable are not implemented. Both lack audio output.

Amiga models a PAL 68000/OCS machine with 512 KiB chip RAM and 512 KiB slow RAM. Kickstart 1.2 is included and can be overridden locally. Copper, blitter, bitplanes, sprites, CIA timers and MFM disk DMA are implemented with approximate timing. Audio output, disk writing/swapping, extended ADF/IPF and AGA are unsupported. Marble Madness boots Workbench: double-click the disk and its game icon. In Turrican, left-click past the intro, then press Fire at the title. Mouse speed 4× suits Workbench; use 1× in game menus.

PS2 and GameCube are C++ ports of the project’s existing Go cores. PS2 uses kernel HLE and optionally a local 4 or 8 MiB BIOS for IOP modules; Jak and Daxter includes its own IOP image. GameCube uses an IPL setup substitute and the disc’s apploader. No firmware is required for the tested GameCube game. Both retain compatibility and rendering limitations of the original cores. Audio, memory-card files, PS2 right-stick and GameCube C-stick input are not exposed.

PS2 capture records GS rendering and transfers; GameCube records GX commands, EFB rendering and display copies. Pixel history describes recorded writes, with GPU register snapshots. Rejected fragments, texture-fetch ancestry and CPU command-buffer ancestry are not recorded. GameCube inspection explains EFB colors before the lossy YUY2 display conversion. Detailed captures can grow the WASM heap beyond 1 GiB; desktop browsers are recommended. These two cores require WebAssembly SIMD and exception handling.

GBA and Dreamcast are C++ ports of the existing Go cores, using BIOS HLE without downloaded firmware. GBA has ARM7TDMI, PPU modes 0–5, affine backgrounds/objects, windows and color effects, DMA, timers and EEPROM. Mosaic, SRAM/Flash chips and link cable are incomplete; timing retains the original instruction-budget model. Dreamcast includes SH-4, AICA ARM7, Maple, GD-ROM HLE and software PowerVR rendering. Its current parser accepts only a combined BIN, with raw Mode 1 data and audio tracks; GDI, CDI, CHD and separate track files are unsupported. PowerVR translucency sorting and other rendering features remain incomplete. Neither port exposes audio output or external battery/VMU saves; use browser states for persistence. Both require WASM SIMD and exception handling.

GBA captures one PPU frame: layer samples, priority/window/color-effect decisions, and historical video-memory/palette writes. Dreamcast captures three video fields to include double-buffer producers: actual VRAM writes, TA commands and PowerVR register snapshots. Its inspector does not yet trace rejected fragments or sampled textures. Replay uses the final display mapping and separate memory. Capture limits and missing evidence are shown.

Firmware and disc layouts

C64 BASIC, KERNAL and character ROMs are hosted here and hash-checked. You can override all three with local files. PS1 and 3DO use incomplete BIOS/OS high-level emulation; no local BIOS file is requested. C64 disk images and CUE pregaps/postgaps are unsupported. The generic disc loader does not accept combined data/audio BIN files; Dreamcast has its own combined-BIN parser. Audio tracks are not played. Select a CUE together with the files it names.

Inspecting a frame

Pause records one complete declared display interval. C64 uses its raster frame; PS1 and N64 currently use synthetic timing boundaries; PS1 captures four fields to include double-buffer producer context; 3DO uses DisplayScreen calls and decoded movie presentations; DS and 3DS use their modeled display frame boundaries. PSP captures between display-buffer presentations. Game Boy captures a complete modeled LCD frame; Game Gear captures its declared VDP frame interval. Amiga captures its modeled PAL raster interval, with historical bitplane, sprite and palette sources, Copper moves and blitter/DMA writes. Blitter inputs and HAM color dependencies do not yet have complete automatic ancestry. Select a pixel to see observed writes and sources. The rendering slider replays captured effects in separate scratch memory. It does not advance the paused machine.

Pre-existing framebuffer contents and missing history are labeled. PS1 semi-transparency and mask-bit effects are incomplete. N64 coverage and scanout are simplified, and texture evidence identifies the last filter tap. 3DO source bytes and PIXC results are recorded without claiming universal instruction-level dataflow. The known Need for Speed profile decodes its requested Cinepak movies through HLE, paced by stream timestamps; movie writes are labeled as HLE in the inspector. The incomplete native DSP/DataStreamer path remains available with compatibility disabled. Replay uses the final display-buffer mapping.

DS firmware is synthesized and BIOS calls use HLE. Toon shading, audio, display capture, fog and edge marking retain the Go core’s limitations. Its inspector records 2D composition and GX polygons in capture-local surfaces. 3DS uses Horizon HLE and requires a decrypted cartridge, without system firmware; CIA and encrypted images are unsupported. Its inspector follows PICA register writes, raster effects and GX transfers in captured graphics RAM. DS/3DS texture-sampler ancestry is not yet recorded. The 3DS renderer is not bit-identical to the Go renderer.

States and controls

States require the same game files, firmware, compatibility settings and exact core build. Select the original media after reloading the page, then load the state. A rejected state leaves the current machine intact. States download locally; they are not cloud saves. Keyboard, on-screen buttons and standard gamepad mappings are available. Controls release when focus is lost. Click or drag the lower DS/3DS screen to use the stylus while running; paused clicks inspect pixels. 3DS arrow keys also drive its circle pad.

Browser validation

Browser workflows have been exercised in Chromium. Safari has passed the hosted C64 firmware, state-import, capture and replay checks. Firefox, the remaining Safari/game combinations and a physical gamepad session still need end-to-end acceptance. Native and Node/WASM tests are reported separately and do not establish browser compatibility. File selection, WebAssembly, module workers and synchronous worker-local File reads are required. Sound output is not part of this release.

Performance counters distinguish emulated progress from frames actually presented. Normal mode aims for native timing; fast-forward removes that pacing. Detailed capture and replay costs are reported separately. The earlier DS reference run reached its interactive title in roughly two minutes. A 3DS cold run reached its title in about a minute in Node/WASM; browser timing varies. A detailed 3DS capture can use over 1.5 GiB of WASM memory. Desktop browsers are recommended for this experimental core. Game Boy and Game Gear have been observed at approximately 60 presented frames/s at normal speed in Chromium. PSP requires WebAssembly SIMD support.
